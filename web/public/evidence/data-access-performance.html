Data access: speed, fallbacks and what to mirror

How the backend finds SPHEREx images, reads pixels and queries catalogues when the remote services are slow or down, with the measurements behind ADR-0057 and a cost comparison of mirroring options. It builds on the per-file chunk cache, IRSA cutouts first and batched reads of ADR-0037 to ADR-0039.

All numbers are from the dev server on 2026-11-15, during an outage: IRSA TAP and SIA answered 502 Proxy Error, ESA's Gaia archive, CDS (SIMBAD TAP, VizieR TAP and ASU) and JPL's sb_ident timed out. IRSA's file server (ibe), IRSA MOST, AWS S3, MAST, the CfA VizieR mirror, NOIRLab Data Lab and IMCCE SkyBoT kept working.

Where each kind of data comes from

Each kind of data has several interchangeable sources (backend/spherex_core/endpoints.py). Every call records latency and outcome; the next call asks the source with the lowest median latency plus a penalty for recent failures and open circuit breakers. Interactive requests hedge: when a source runs past about 1.5× its p90, the next one starts alongside and the first answer wins. A source whose breaker is open is skipped; the last source left gets one 30 s attempt instead of two 10 s ones. GET /api/status/upstreams shows the current order, p50/p90 latency, success rate, last error and the breakers (api.md).

The file-catalogue mirror

archive/mirror.py keeps a SQLite table of every SPHEREx Level 2 file with an R-tree over its footprint. It is built from the public bucket alone: list the keys, read the first 32 KiB of each new file and take the footprint from the file's own WCS (SIP included), so it needs nothing from IRSA.

Before and after

"Before" is the dev API with the code of main plus #18 at the same moment; "after" is this branch on a spare port with the same cache directory (catalogue cones are cached per position, so each row used a field neither had cached).

The known-object fallback is a degraded answer: SkyBoT cannot place the observer on SPHEREx, so its positions are geocentric (off by up to 9.7″/D for an object D AU away) and its rates miss the spacecraft's orbital motion (37″/h ÷ D). Such objects carry geocentric: true, their position error includes the parallax, the motion tolerance includes the orbital term, the overlay's observer says so, and the answer is cached apart so the next query asks JPL again.

Not covered: archival epochs of fields never built still need IRSA's image search, so they failed during the outage for the four non-preset prewarm fields (the presets were cached); that fallback is separate work.

Popular fields and the persistent tier

  • targets/popular.json: the five presets plus 16 well-known fields (nearby stars and brown dwarfs, variables, young stars, nebulae and galaxies, two moving objects). Fields requested ≥ 5 times (SPHEREX_POPULAR_PROMOTE_AFTER) are promoted automatically; counts live in Redis or <cache>/popular/.
  • scripts/prewarm_popular.py builds them as pinned jobs at prewarm priority, one at a time, with archival epochs and catalogue cones.
  • scripts/cutout_tier.py bundles a sequence's result, its per-file chunks, legacy cutouts and detector tables into checksummed tar parts (≤ 240 MB) and pushes them to Cloudflare R2 through a machine logged in with wrangler; the server holds no credentials. fetch + pull restore them on a new server (pull also reads a public bucket URL, if the bucket is given one).

The nine tier fields (five presets, Proxima Centauri, Wolf 359, Luhman 16, Mira) make 1.80 GB in 12 parts plus a manifest each. The five presets (1.10 GB, 8 parts) are in the R2 bucket planet-x-spherex-tier; the other four (0.70 GB) are bundled on the dev server and go up with cutout_tier.py push <ids> (the upload streams through the logged-in machine, ~1 MB/s from a home connection; push retries a failed part and --skip-parts resumes).

What to mirror, and what it costs

The archive on 2026-11-15: DR1 76.9 TB, QR3 29.2 TB, 1.63 M files of 65 MB on average (106 TB in the collections we search), growing ~1.4 TB per week (~6 TB per month). 1 TB holds ~15,300 files, 0.94 % of the archive.

Option Size Monthly cost Notes
File-catalogue mirror (this PR) 1.0 GB ~$0.09 on vast.ai disk, ~$0.15 on a Railway volume removes the dependency on IRSA TAP; refresh 13 s/hour
Popular-field tier in R2 (this PR) 1.1 GB (1.8 GB with all nine fields) $0 (R2 free tier: 10 GB-month, 1 M writes, 10 M reads) $0.015/GB-month beyond 10 GB
1 TB of pixels in R2 1 TB ~$15 writes $4.50/M (15,300 files: $0.07 once), reads $0.36/M, no egress fees
1 TB in a Railway Bucket 1 TB ~$15 $0.015/GB-month, egress and operations free
1 TB on the vast.ai instance disk 1 TB ~$93 $0.093/GB-month, fixed when the instance is created, lost with it
1 TB on a Railway volume 1 TB ~$150 $0.15/GB-month, plus $0.05/GB service egress
The whole archive in R2 106 TB, +6 TB/month ~$1,590, +$90 every month duplicates a bucket that is already free to read
AWS S3 open data (what we read now) — $0 no egress fees on the open-data bucket; 0.13 s per range read from the dev server

Recommendation: keep reading pixels from the AWS open-data bucket (free, fast, and it stayed up while IRSA did not), with IRSA ibe as its automatic fallback. Keep the 1 GB file-catalogue mirror on every server, and keep only the popular fields' pixels in R2 (a few GB, inside the free tier). A 1 TB pixel mirror would only help if S3 and IRSA ibe were both unreachable, and the per-file chunk cache of ADR-0037 already keeps what has been read; if it is ever wanted, R2 or a Railway Bucket (~$15/month) are the right places, never instance disk or volumes.
